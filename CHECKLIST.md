# Hot Cross Buns development checklist

This is the repository's single source of truth for planned work and release readiness. It covers a release-quality Linux and macOS product with a CLI/TUI and windowed desktop apps, followed by a deferred Windows port, in **one repository**. Performance work follows measured user-facing bottlenecks. An unchecked item is work to plan or verify, not a claim that the current implementation is broken. New work, changes in scope, and completed acceptance criteria belong here rather than in a parallel issue roadmap.

The former native-wrapper issues [#423](https://github.com/gongahkia/hot-cross-buns/issues/423) and [#424](https://github.com/gongahkia/hot-cross-buns/issues/424) are superseded by the acceptance and release work below. Their rule that Linux work must wait for macOS acceptance does not apply to this Linux/macOS plan.

## Architecture direction

Keep the local Python domain, accounts, OAuth, SQLite storage and migrations, sync, and application services in a UI-independent shared core. The existing `hcb` CLI/TUI and future desktop apps are separate frontends of that core; the CLI is a frontend, not the backend. A hosted service is not required for this local-first design. Desktop frontends should use a bounded, versioned local bridge to the Python core rather than opening its SQLite database or credential files themselves.

The measured Fedora core/database optimization pass and historical source restoration are complete enough to begin desktop prototypes; remaining core contracts and release checks continue during integration. Reuse the restored Swift frontend in [`frontends/macos/`](frontends/macos/) for macOS and prototype [`frontends/qt/`](frontends/qt/) for Linux, with [`frontends/electron/`](frontends/electron/) as a fallback if Qt proves unsuitable. Develop macOS and Linux first. Defer Windows implementation and verification until those ports work; prefer reuse of a successful Qt frontend before considering a separate Windows toolkit. Preserve `hcb` throughout. Keep everything in this repository for now; consider a dedicated core repository only once its API, data compatibility policy, and release cadence are stable enough to version independently.
