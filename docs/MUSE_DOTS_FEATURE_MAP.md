# Muse and dots feature map for Gator

Researched 2026-10-17. This is a product comparison, not a claim that either competitor works perfectly in every case. It uses [Meta's Muse launch][muse-launch], [Muse's design account][muse-design], [Meta's security account][muse-security], and [OpenAI's dots documentation][dots-overview]. Meta's [Connect 2026 announcement][muse-connect] is labeled separately where it describes future features. Gator status reflects this repository's implementation as of 2026-10-18; it is an implementation audit, not a live quality benchmark.

The product goal remains a **terminal-native personal agent that remembers goals, works across selected local and connected sources, and follows through over time**. Feature parity is useful only when the same user job works reliably. In particular, a saved goal is not proof of useful follow-through, a connector is not event monitoring, a generated draft is not a completed external action, and a local supervisor is not an always-on cloud agent.

**Status key:** **Present** means the capability exists with the stated boundary; **Partial** means Gator has a relevant component but cannot deliver the full user outcome; **Absent** means no comparable product workflow was found. Priorities are recommendations for Gator, not the competitors' plans: **P0** prove value, **P1** first useful recurring loop, **P2** expand it, **Later** requires a separate product or infrastructure decision.

The compact source labels in the tables identify the linked documents: **M1** Muse design, **M2** Muse launch, **M3** Muse security, **M4** Meta's later Connect announcement; **D1–D5** OpenAI dots documentation; **G1–G8** Gator repository documentation. The links beside each label open the specific source.

## Status at a glance

Of the 28 capabilities below, **5 are present with stated limits, 18 are partial, and 5 are absent**. These are implementation classifications, not measured success rates. The partial items are:

| Area | Partial capabilities | Main remaining proof or capability |
| --- | --- | --- |
| Goals and follow-through (6) | Turn a request into a durable goal and plan; notice a change and revise the next step; event monitoring in apps; work while the user is away; decide when to be quiet; propose useful work before being asked | Prove useful goal setup, relevant changes and next steps, and quiet follow-up in live use. App watches poll, and local work stops when the host is off. |
| Conversation and memory (5) | One continuing relationship with separate task contexts; accept interruptions and concurrent requests; delegate specialist work and follow up; remember preferences and ongoing context; reusable skills and tools | Make concurrent conversations and direct task follow-up usable; measure scoped recall and whether selected specialists or skills improve outcomes. |
| Sources and actions (4) | Read across connected services; connect facts across sources into a useful answer; take external actions across apps; browser navigation and account handoff | Validate connected reads and cross-source answers on real accounts; broaden approved actions only with reliable receipts and recovery. |
| Trust and control (3) | Keep credentials outside model context; inspect activity, steer, stop, and recover; control interruption level and destination | Test secret and prompt-injection boundaries and whether users can recover work. Collect ratings for shown alerts and audit quiet decisions for missed changes; delivery and urgency policies remain limited. |

Alert feedback now covers two distinct samples: `gator job inbox rate` or interactive `/inbox rate` records judgments on **shown** job alerts, and `gator job quiet-audit` lets a user inspect and label **model-evaluated quiet** watch attempts. The interactive inbox reloads on opening and displays IDs, read state, and ratings so those judgments can be made without leaving terminal chat. Unchanged-input skips have no new model decision. Neither partial status changes: no real review sample or full ground-truth set exists, so alert precision and missed-change recall remain unmeasured.

## What the comparison implies

The largest remaining product gap is **proving that a connected change leads to a useful next action**. Gator can retain a goal, poll bounded selected connected sources while its local supervisor runs, create drafts, and ask for approval. The content gate has deterministic tests, but live relevance, missed-change rate, and whether a user would trust the resulting decision or draft remain unmeasured. This is the first parity slice to validate and improve. It serves the user's stated use cases: daily briefs, slide decks, and email drafts, and it still makes sense in a terminal.

The second gap is **quality evidence**. The [25-case continuity corpus][gator-continuity] has scripted 25/25 for both Gator and a same-model no-goal baseline. The [eight-case cross-source corpus][gator-cross-source] has scripted 8/8 for both arms. These scripted runs validate fixtures and graders; their model responses are supplied by scripts. A 2026-10-17 three-case continuity smoke run passed one case and hit provider quota errors on two; its baseline arm did not run. A 2026-10-18 matched attempt passed two cases in Gator's goal arm, but one hit Gemini HTTP 503 and all three baseline cases hit HTTP 429 under a reported 20-request daily free-tier limit. The comparator now excludes provider-failed cases from outcome deltas; this attempt had zero comparable cases. Local watch and connector tests prove wiring and selected safety boundaries, not whether Gator spots important changes or helps a person finish a goal. This map should not be converted into a “percent parity” score.

Some competitor capabilities are distribution or infrastructure choices, not necessary ingredients of a useful CLI agent: cloud operation while a laptop is off, phone/WhatsApp/Slack/Teams access, voice, avatars, glasses, payments, and rich interactive UIs. Claiming direct parity on those would be misleading. Gator's distinctive bet can be a small, inspectable agent that works in the terminal and on the user's files, but [lower RAM remains a target][gator-runtime] until measured on comparable tasks.

## Ordered work and proof

1. **P0: Measure an honest baseline.** Run the cross-source and continuity corpora with a live model and a same-model no-goal baseline when provider capacity is available. Human-blind grade goal progress, correct next step, evidence support, forbidden actions, alert precision/recall, user rework, elapsed time, model requests, and peak RSS. Preserve raw traces and count failures, including quota and tool failures. The scripted 8/8 and 25/25 results are harness checks.
2. **P1: Prove one connected recurring loop.** A user can establish an offsite-planning or daily-brief goal with selected Gmail and Calendar reads; bounded polling, item-level change records, a draft, configured connector readiness in activity, ratings for surfaced job alerts, and a quiet-watch audit are wired. Test actual connected reads against relevant changes, duplicate messages, ambiguous timestamps, expired access, and quiet days. Collect ratings for shown alerts and review the quiet decisions against source truth; unreviewed and unchanged-input checks cannot be assumed correct. Show a source-supported next step without noisy alerts. Configured readiness cannot prove that an API request will succeed.
3. **P1: Make the loop legible in terminal chat.** Goal activity shows the last check, next check, latest detected change, selected connector status, latest specialist checkpoints, inbox items, suggestions, and pause/resume controls. The Work activity CLI and `/activity` in terminal chat now join running runs, specialist checkpoints, and pending decision IDs. Cross-terminal steering of active LLM specialists is wired. Test whether users can understand, steer, and recover work without digging into job IDs.
4. **P1/P2: Finish memory and action recovery.** Local file-linked memories now become unavailable for automatic recall when their file changes or disappears; measure wrong recall and extend validation to other source types. The narrow Gmail send path has exact foreground approval, a receipt for successful sends, and a manual read-scoped Sent check for uncertain sends. Validate the check with a real Gmail account; then add receipts for other actions and idempotency where a provider supports it. Never automatically retry an uncertain send.
5. **Later: Make explicit product decisions.** Cloud continuity, standing action grants, messaging channels, voice/identity, and purchases remain absent. Evaluate each after the local recurring loop has live outcome evidence. They require distinct hosting, authority, integration, interface, or payment designs; local components do not imply parity.

**First concrete acceptance scenario:** A user says, “Keep track of the offsite; watch these local notes, my selected planning emails, and next week's calendar. Tell me only if a venue or deadline changes, and draft the necessary reply.” Gator confirms the watch and access scope. A venue cancellation arrives while the terminal is closed but the host is online. On the next check, Gator links the changed message to the goal, identifies the affected plan step, prepares a reply with the correct date and source, and surfaces one notification. It stays quiet on an unrelated email and after a restart. It never sends the reply without an approved send capability. The same scenario should be graded against a no-goal baseline and replayed with a misleading instruction in the email body.
