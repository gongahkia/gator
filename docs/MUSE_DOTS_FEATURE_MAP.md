# Muse and dots feature map for Gator

Researched 2026-10-17. This is a product comparison, not a claim that either competitor works perfectly in every case. It uses [Meta's Muse launch][muse-launch], [Muse's design account][muse-design], [Meta's security account][muse-security], and [OpenAI's dots documentation][dots-overview]. Meta's [Connect 2026 announcement][muse-connect] is labeled separately where it describes future features. Gator status is based on this repository's code and docs at commit `a8892d0ac`; it is an implementation audit, not a live quality benchmark.

The product goal remains a **terminal-native personal agent that remembers goals, works across selected local and connected sources, and follows through over time**. Feature parity is useful only when the same user job works reliably. In particular, a saved goal is not proof of useful follow-through, a connector is not event monitoring, a generated draft is not a completed external action, and a local supervisor is not an always-on cloud agent.

**Status key:** **Present** means the capability exists with the stated boundary; **Partial** means Gator has a relevant component but cannot deliver the full user outcome; **Absent** means no comparable product workflow was found. Priorities are recommendations for Gator, not the competitors' plans: **P0** prove value, **P1** first useful recurring loop, **P2** expand it, **Later** requires a separate product or infrastructure decision.

The compact source labels in the tables identify the linked documents: **M1** Muse design, **M2** Muse launch, **M3** Muse security, **M4** Meta's later Connect announcement; **D1–D5** OpenAI dots documentation; **G1–G7** Gator repository documentation. The links beside each label open the specific source.

## What the comparison implies

The largest product gap is **the closed loop from a live signal to a useful next action**. Gator can retain a goal, read selected apps in a foreground Work run, schedule local jobs, create drafts, and ask for approval. It cannot yet attach a connected source to a goal watch, notice a relevant app change across restarts, reconcile that change with the goal, and bring the user a timely, evidence-backed draft or decision. That is the first parity slice worth building. It serves the user's stated use cases: daily briefs, slide decks, and email drafts, and it still makes sense in a terminal.

The second gap is **quality evidence**. The [25-case continuity corpus][gator-continuity] has scripted 25/25 for both Gator and a same-model no-goal baseline; the live comparison has not been run. Local watch tests prove wiring and safety boundaries, not whether Gator spots important changes or helps a person finish a goal. This map should not be converted into a “percent parity” score.

Some competitor capabilities are distribution or infrastructure choices, not necessary ingredients of a useful CLI agent: cloud operation while a laptop is off, phone/WhatsApp/Slack/Teams access, voice, avatars, glasses, payments, and rich interactive UIs. Claiming direct parity on those would be misleading. Gator's distinctive bet can be a small, inspectable agent that works in the terminal and on the user's files, but [lower RAM remains a target][gator-runtime] until measured on comparable tasks.

## Ordered work and proof

1. **P0: Measure an honest baseline.** Run 10–15 longitudinal, live-model goal scenarios against the same-model no-goal baseline: source changes, missed deadlines, changed preferences, stale facts, prompt injection, tool failure, and quiet days. Human-blind grade goal progress, correct next step, evidence accuracy, forbidden actions, alert precision/recall, user rework, elapsed time, model requests, and peak RSS. Preserve raw traces and count failures, not just final prose. A scripted fixture passing is a harness check.
2. **P1: Build one connected recurring loop.** Let a user establish an offsite-planning or daily-brief goal with selected Gmail and Calendar reads; save bounded source cursors and a watch policy; poll while the local supervisor is available; reconcile new/changed items with the plan; prepare a cited brief or email draft; surface only a changed decision or needed approval. Recover across restart, expired access, duplicate messages, and ambiguous timestamps. Gmail send remains unavailable until a separately reviewed action feature exists.
3. **P1: Make the loop legible in terminal chat.** Capture a proposed goal from conversation, confirm its source/schedule/notification scope, and present a compact activity view with last check, next check, latest evidence, pending suggestions, pending approvals, and pause/resume. A user should not need to inspect job IDs to understand a goal.
4. **P1/P2: Improve memory and action quality.** Use source-linked memory with correction/expiry tests, then add one narrow external action with a durable intent, exact approval, idempotency key where supported, reconciliation after uncertain results, and an audit receipt. Add standing permission only after the exact-action path has measured reliability.
5. **Later: Make explicit product decisions.** Decide separately whether cloud continuity, messaging channels, browser account handoff, interactive artifacts, or voice are worth building. Each adds infrastructure and trust costs; none should be counted as “almost there” because Gator has a local daemon or a text skill.

**First concrete acceptance scenario:** A user says, “Keep track of the offsite; watch these local notes, my selected planning emails, and next week's calendar. Tell me only if a venue or deadline changes, and draft the necessary reply.” Gator confirms the watch and access scope. A venue cancellation arrives while the terminal is closed but the host is online. On the next check, Gator links the changed message to the goal, identifies the affected plan step, prepares a reply with the correct date and source, and surfaces one notification. It stays quiet on an unrelated email and after a restart. It never sends the reply without an approved send capability. The same scenario should be graded against a no-goal baseline and replayed with a misleading instruction in the email body.
