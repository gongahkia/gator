# Muse and dots feature map for Gator

Researched 2026-10-17. This is a product comparison, not a claim that either competitor works perfectly in every case. It uses [Meta's Muse launch][muse-launch], [Muse's design account][muse-design], [Meta's security account][muse-security], and [OpenAI's dots documentation][dots-overview]. Meta's [Connect 2026 announcement][muse-connect] is labeled separately where it describes future features. Gator status reflects this repository's implementation as of 2026-10-17; it is an implementation audit, not a live quality benchmark.

The product goal remains a **terminal-native personal agent that remembers goals, works across selected local and connected sources, and follows through over time**. Feature parity is useful only when the same user job works reliably. In particular, a saved goal is not proof of useful follow-through, a connector is not event monitoring, a generated draft is not a completed external action, and a local supervisor is not an always-on cloud agent.

**Status key:** **Present** means the capability exists with the stated boundary; **Partial** means Gator has a relevant component but cannot deliver the full user outcome; **Absent** means no comparable product workflow was found. Priorities are recommendations for Gator, not the competitors' plans: **P0** prove value, **P1** first useful recurring loop, **P2** expand it, **Later** requires a separate product or infrastructure decision.

The compact source labels in the tables identify the linked documents: **M1** Muse design, **M2** Muse launch, **M3** Muse security, **M4** Meta's later Connect announcement; **D1–D5** OpenAI dots documentation; **G1–G8** Gator repository documentation. The links beside each label open the specific source.

Recognition quality and source/schedule UX still need live evaluation. [G1][gator-direction] | **P1.** From one chat request, reliably propose the right goal, plan, source, and follow-up policy; resume it naturally in chat. |
| Notice a change and revise the next step | Advances goals when things change; can suggest plan adjustments [M1][muse-design] | Pauses and wakes adaptively; can respond to supported events [D2][dots-tasks] | **Partial.** A bounded local or connected watch detects content changes and may propose a reviewed plan edit; useful next-step judgment is unmeasured. [G1][gator-direction] | **P1.** For a chosen connected source, detect a material change, cite it, update the proposed next step, and avoid acting on stale information. |
| Fixed recurring work | Schedules continued work [M1][muse-design] | Saved schedules with timing, timezone, notification condition, and destination [D2][dots-tasks] | **Present locally.** Goal-linked cron jobs and a per-user supervisor run while the host/user manager is active. [G2][gator-jobs] | **P1.** Make scheduling conversational and show the exact saved task, next run, and delivery policy. |

Calendar now reads every page of the selected moving window up to 500 events and fails on overflow or invalid pagination. Google's sync token cannot be combined with that time window, so Calendar has no provider cursor. None of these watches has a push subscription. [G1][gator-direction] | **P1.** Evaluate relevance and missed changes on real accounts and keep watch scope explicit. A Calendar cursor would require a broader calendar cache and separate window filtering. Do not call polling a push subscription. |
| Work while the user is away | Background work continues after Muse app closes [M1][muse-design] | Cloud work continues while devices are off [D3][dots-computers] | **Partial.** Local per-user service survives CLI exit, but cannot run with the host off. [G2][gator-jobs] | **Later.** First prove that follow-up is valuable on an online machine; cloud continuity would need separate hosting, credential, and trust architecture. |
| Decide when to be quiet | Surfaces work only when meaningfully new; adjustable proactivity [M1][muse-design] | User specifies which changes deserve updates and which decisions need input [D2][dots-tasks] | **Partial.** Exact duplicate suppression, unchanged-input skips, model-chosen quiet watch results, and per-goal desktop mute/quiet hours exist. Attention summaries show up to two model-supplied references only when they match retained source evidence, an observed connected item, or a current plan step; unsupported references are flagged for review. Reference integrity does not prove claim support. Semantic false-alert and missed-alert rates are unmeasured. [G1][gator-direction] | **P0/P1.** Evaluate false alerts and misses on changed and quiet days; verify claim support and add urgency. |
| Propose useful work before being asked | Onboarding tips, Ideas area, and goal-based suggestions [M1][muse-design] | Proactive read-only research and suggested next steps [D2][dots-tasks] | **Partial.** Work can queue a note, skill, plan, or schedule suggestion for review or rejection. `gator suggestion show` now checks note and plan references against retained Work evidence and current local files, but reference integrity does not prove claim support. Idea discovery, acceptance, and onboarding quality are unmeasured. [G3][gator-knowledge] | **P2.** Show a few source-supported, dismissible suggestions tied to a real goal. Measure acceptance and user rework. |

[G3][gator-knowledge] | **P1.** Preserve these controls as retrieval improves; show why each recalled memory was used and assess whether its claim is still supported. |
| Reusable skills and tools | Can use its own computer/terminal to build tools for a task [M1][muse-design] | Plugins and local skills on a connected computer [D3][dots-computers] | **Partial.** User-created text skills, extensions, MCP, and tools exist, but skills cannot grant authority or create a general execution environment. [G3][gator-knowledge] | **P2.** Test whether relevant skills are chosen and help. Expand tool creation only inside bounded execution and reviewed permissions. |

Gmail watches use a bounded history cursor to avoid rereading unchanged message details, with a full scan after cursor expiry. Calendar reads up to 500 events across the selected moving window's pages; the window is incompatible with Google's sync token. New Google OAuth goal checks pin a digest of the live OIDC account subject, allowing same-account reauthorization while failing closed on account switches before each connected read. Existing refresh-grant pins retain their stricter behavior; older unpinned checks still run and are flagged in activity. Goal activity shows configured access and recovery hints; `gator goal access ID` performs a separate bounded live read of selected watch sources without retaining their content or changing the watch state. A successful probe proves only momentary access. Connected-watch relevance and real API reliability remain unproven. [G5][gator-google] [G1][gator-direction] | **P1.** Measure actual connected-watch reliability, recover from expired access, and prove relevance on real account changes. A Calendar cursor requires a broader cache design. |

An eight-case, two-turn corpus now covers changed mail, calendar, and notes, including conflicting facts, withdrawn consent, prompt injection, and irrelevant noise. Both scripted arms passed 8/8, which checks fixture and grader wiring; no live-model cross-source quality or real API reliability is established. [G5][gator-google] [G8][gator-cross-source] | **P1.** Run the corpus live against a same-model baseline; grade decisions, source support, drafts, and quietness by blind human review. |
| Create and edit documents, decks, and data | Documents, PDFs, web pages, trackers, and interactive artifacts [M1][muse-design] | Cloud computer supports documents/data work and files [D3][dots-computers] | **Present for local artifacts.** DOCX, XLSX, PDF, PPTX, and other staged files have bounded writers/validation; rich live interfaces are absent. [G6][gator-capabilities] | **P2.** Prioritize usefulness and quality of deliverables; treat interactive apps as a separate surface choice. |
| Take external actions across apps | Email, booking, forms, purchases, and other connected tasks with approval [M2][muse-launch] | Permitted app/computer actions; automatic review and user handoff when required [D4][dots-controls] | **Partial.** Docs/Sheets and a narrow Gmail send operation require foreground exact-action approval. Gmail send has a separate opt-in scope and never runs in scheduled jobs; Calendar cannot change events. Successful sends retain Gmail's message ID; every new send retains a unique MIME reconciliation ID. For an uncertain send, `gator work reconcile` can perform an explicit read-only Sent lookup and retain its latest result. It does not prove recipient delivery or retry. Individual Docs/Sheets actions retain Google's returned resource ID and response digest; a missing or mismatched ID yields an uncertain outcome. [G7][gator-browser] | **Later.** Expand only for a tested workflow that connector APIs cannot cover, with origin, credential, and action boundaries. |
| Work on a user's local computer | Muse has its own VM, rather than a Gator-style local primary surface [M2][muse-launch] | Optional connected local computer while online and app open [D3][dots-computers] | **Present in a narrower form.** Gator starts in the user's local terminal; selected browser and macOS app sessions require foreground setup and approvals. [G6][gator-capabilities] | **P2.** Keep terminal and local files as the advantage; measure usability and resource cost. |
| Keep a dedicated cloud workspace | Per-person secure VM with files/browser [M2][muse-launch] | Cloud computer with persistent files/software/browser, even when devices are off [D3][dots-computers] | **Absent.** Gator is local-first and has no hosted workstation or cross-device execution. [G6][gator-capabilities] | **Later.** A hosted companion would be a new product architecture and cost model, not a parity patch. |

## What the comparison implies

The largest remaining product gap is **proving that a connected change leads to a useful next action**. Gator can retain a goal, poll bounded selected connected sources while its local supervisor runs, create drafts, and ask for approval. The content gate has deterministic tests, but live relevance, missed-change rate, and whether a user would trust the resulting decision or draft remain unmeasured. This is the first parity slice to validate and improve. It serves the user's stated use cases: daily briefs, slide decks, and email drafts, and it still makes sense in a terminal.

The second gap is **quality evidence**. The [25-case continuity corpus][gator-continuity] has scripted 25/25 for both Gator and a same-model no-goal baseline. The new [eight-case cross-source corpus][gator-cross-source] has scripted 8/8 for both arms. These scripted runs validate fixtures and graders; their model responses are supplied by scripts. A three-case continuity live smoke run passed one case and hit provider quota errors on two; its baseline arm did not run. Local watch and connector tests prove wiring and selected safety boundaries, not whether Gator spots important changes or helps a person finish a goal. This map should not be converted into a “percent parity” score.

Some competitor capabilities are distribution or infrastructure choices, not necessary ingredients of a useful CLI agent: cloud operation while a laptop is off, phone/WhatsApp/Slack/Teams access, voice, avatars, glasses, payments, and rich interactive UIs. Claiming direct parity on those would be misleading. Gator's distinctive bet can be a small, inspectable agent that works in the terminal and on the user's files, but [lower RAM remains a target][gator-runtime] until measured on comparable tasks.

## Ordered work and proof

1. **P0: Measure an honest baseline.** Run the cross-source and continuity corpora with a live model and a same-model no-goal baseline when provider capacity is available. Human-blind grade goal progress, correct next step, evidence support, forbidden actions, alert precision/recall, user rework, elapsed time, model requests, and peak RSS. Preserve raw traces and count failures, including quota and tool failures. The scripted 8/8 and 25/25 results are harness checks.
2. **P1: Prove one connected recurring loop.** A user can establish an offsite-planning or daily-brief goal with selected Gmail and Calendar reads; bounded polling, item-level change records, a draft, and configured connector readiness in activity are wired. Test actual connected reads against relevant changes, duplicate messages, ambiguous timestamps, expired access, and quiet days. Show a source-supported next step without noisy alerts. Configured readiness cannot prove that an API request will succeed.
3. **P1: Make the loop legible in terminal chat.** Goal activity shows the last check, next check, latest detected change, selected connector status, latest specialist checkpoints, inbox items, suggestions, and pause/resume controls. Add live task steering and a pending action approval view; test whether users can understand and interrupt work without digging into job IDs.
4. **P1/P2: Finish memory and action recovery.** Local file-linked memories now become unavailable for automatic recall when their file changes or disappears; measure wrong recall and extend validation to other source types. The narrow Gmail send path has exact foreground approval, a receipt for successful sends, and a manual read-scoped Sent check for uncertain sends. Validate the check with a real Gmail account; then add receipts for other actions and idempotency where a provider supports it. Never automatically retry an uncertain send.
5. **Later: Make explicit product decisions.** Cloud continuity, standing action grants, messaging channels, voice/identity, and purchases remain absent. Evaluate each after the local recurring loop has live outcome evidence. They require distinct hosting, authority, integration, interface, or payment designs; local components do not imply parity.

**First concrete acceptance scenario:** A user says, “Keep track of the offsite; watch these local notes, my selected planning emails, and next week's calendar. Tell me only if a venue or deadline changes, and draft the necessary reply.” Gator confirms the watch and access scope. A venue cancellation arrives while the terminal is closed but the host is online. On the next check, Gator links the changed message to the goal, identifies the affected plan step, prepares a reply with the correct date and source, and surfaces one notification. It stays quiet on an unrelated email and after a restart. It never sends the reply without an approved send capability. The same scenario should be graded against a no-goal baseline and replayed with a misleading instruction in the email body.
